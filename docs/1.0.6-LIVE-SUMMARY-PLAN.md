# 1.0.6 plan: live meeting summary and easy local text models

Status: development plan for 1.0.6, which builds on 1.0.5. Nothing described here is released.

## Goal

While a meeting is still being recorded, a side panel shows a running summary. It stays short at all times, and nothing said in the meeting is dropped from it. The panel covers:

- what has been discussed so far
- decisions
- tasks
- open questions
- who said it, as far as the audio tracks show that honestly

Someone who comes back after 30 minutes, or who is asked "what did we discuss?", can read the panel out loud. At the end of a meeting, the closing summary is already prepared.

A local text model is the default. A cloud model, or a company endpoint that speaks the OpenAI chat API, can be used only after explicit text release for that meeting. AGENTS.md requires this.

## Why a rolling, source-linked design

Sending the whole transcript to the model again on every update does not work well:

- It gets slower with every minute of the meeting.
- A small local model runs out of context after about 20–40 minutes.
- Each run can quietly drop points the previous run had.

So the live summary has two layers.

1. **Window extraction (append-only).**
   - Only new confirmed transcript sections since the last update form a window.
   - A window holds at most 6,500 characters, the same budget as post-meeting analysis.
   - One model call per window returns four lists:
     - important points and insights
     - decisions
     - tasks
     - open questions
   - Every statement has to pass the existing literal source check: a known `sourceId` plus a verbatim quote. Tasks may name an owner or a due date only when that value appears literally in the quote.
   - Accepted statements are stored and never rewritten. Nothing is lost because a later answer forgets it.
   - The model also receives the texts of statements already found, but only so that it does not repeat them.
2. **Rolling overview (compact).**
   - After each window, a second, small call rewrites the overview: at most 8 bullet points of the meeting so far.
   - Its input is the previous overview plus the statements just accepted, both with their evidence. The input therefore stays bounded however long the meeting runs.
   - Each overview bullet has to cite evidence copied from those inputs. It is checked literally against the stored transcript sections of the run.

If the model falls behind the conversation, windows are processed one after another until the backlog is gone. No section is skipped. When the recording stops, the panel keeps updating until catch-up recognition has finished. A final overview then covers the complete meeting.

## When an update runs

The trigger rules are a pure, tested function (`meeting_notes::live::decide`). An update runs when there is new confirmed text and one of these holds:

| Trigger | Rule (defaults) |
| --- | --- |
| Interval | At least the chosen interval (1–15 min, default 3) since the last update, and at least 200 new characters |
| Long contribution | One audio track spoke continuously for 90 s or more and the other track has now replied, with at least 600 new characters |
| A lot of new speech | 4,000 new characters (about 5 minutes of speech), whatever the interval |
| Manual | The user clicks "Update now" |
| End of meeting | Recording and catch-up are finished and unprocessed text remains |

Only one model request runs at a time. Live notes never pause or slow audio capture or speech recognition. The worker only reads the session state that the UI already reads.

## Who said what

Statements show where their evidence came from. This is derived from the cited sections, never invented by the model:

- **Microphone** for your own microphone
- **Computer audio** for other participants

Computer audio can contain several people. Names appear only when they are part of a literal quote. The existing rules against invented speaker counts or speaker statistics stay in the prompt.

## Storage and recovery

Live notes live in `sessions/<meeting>/live-notes/<run>/`. Every file is created atomically and is never overwritten:

- `run.json`: model, local/cloud mode, endpoint, live prompt version, language and creation time. No keys or transcript text.
- `window-000001.json`, …: the exact transcript sections the model saw, plus the accepted statements and the counts of rejected ones.
- `overview-000001.json`, …: each rolling overview.

Reading checks every stored statement strictly again. A damaged file blocks the run and is reported. It is never silently shortened or deleted. After a restart, the same meeting continues the same run if model, mode, endpoint and prompt version match. Otherwise the earlier run stays readable and a new run starts.

A cloud run never continues on its own after a restart. Text release has to be given again, and the key is never stored in the run.

## User interface

- On the recording page, the transcript is on the left and **Live summary** is on the right.
- Below about 1,000 px window width, for example on half a screen, the panel sits above the transcript. A focus button hides the transcript so the summary fills the page.
- Panel contents, top to bottom:
  - state: off, waiting for text, updating, the time of the last update and an estimate of the next one;
  - model, with a local or cloud badge;
  - **Summary so far**, **Decisions**, **Tasks**, **Open questions**, **Important points** (newest first, with section time and track);
  - expandable evidence for every statement.
- Controls: start and stop, **Update now**, an interval selector, and **Copy** for plain text that is ready to read out or paste.
- Optional: "Start automatically with every recording (local models only)".
- The panel keeps the AI-draft notice: evidence confirms quotes, not that the interpretation is correct.

## Easy local text models (presets)

- **Ollama** (`http://127.0.0.1:11434/v1/`) and **LM Studio** (`http://127.0.0.1:1234/v1/`) are one-click presets.
- The app checks both ports on loopback, without DNS or a proxy, shows which one is running, and lists its downloaded models.
- **Model recommendation from installed memory.** The app reads physical RAM and suggests:

  | RAM | Suggestion | Note |
  | --- | --- | --- |
  | Less than 8 GB | Live summary not recommended | Use a remote company endpoint, or analyse after the meeting |
  | 8 to under 16 GB | `gemma4:e2b` | Smallest; may be slow while recording |
  | 16 GB or more | `gemma4:e4b` | Default |
  | 32 GB or more | `gemma4:e4b` | Larger models are an explicit choice |

  Download sizes and speed depend on the model build. The app shows the suggestion and does not download by itself.
- With Ollama, **Download recommended model** asks the local Ollama to pull the model (`/api/pull` on loopback only) and shows its progress. With LM Studio, the panel shows the model name to search for in LM Studio.
- Endpoint and model of a local choice are remembered. Cloud settings and keys are never stored this way; keys stay in the operating system credential store, as before.

## Privacy and safety rules (unchanged and enforced)

- Local transport allows loopback only, with no DNS, no proxy and no redirects. Cloud requires HTTPS and explicit text release for this meeting's live summary.
- No audio, file paths or session objects are sent. Transcript text and model output are data, never instructions.
- Recordings, transcripts and journals are never changed or deleted by this feature.

## Tests

- **Unit:**
  - trigger rules;
  - stable source IDs when tracks complete out of order or a section text is revised;
  - window budget and backlog;
  - per-list validation, including tasks with invented owners;
  - overview evidence must exist;
  - append-only storage;
  - damaged files block instead of shrinking;
  - continuation and refusal to mix model or prompt versions.
- **Integration (synthetic):** a scripted local OpenAI-compatible server drives several windows, overviews and the end-of-meeting update.
- **Desktop service:** start, stop and refresh, cloud without release refused, and recording keeps running while the model fails.
- **UI (vitest):** panel states, consent gate, copy text, evidence, presets and the memory recommendation.
- **Not possible in the build container:** a real local reference run with Gemma, because model downloads are blocked there. AGENTS.md requires that run before release. It stays an open release item.
